# ترتیب اجرای اصلاحات کلینیک

این سند ترتیب تأییدشدهٔ کاربر در ۲۰۲۶-۱۰-۰۴ است. انجام یک مرحله به معنی تکمیل مراحل بعدی نیست. تا موفقیت Regression کل تغییرات، نسخهٔ نهایی منتشر نمی‌شود.

| مرحله | خروجی و شرط پذیرش | وضعیت فعلی |
|---|---|---|
| ۱. Audit و Backup | Git و تطبیق کد نصب‌شده، ساختار واقعی DB، شمارش‌ها، مجموع مالی، انبار، مجوزها و نسخهٔ پشتیبان | Audit زنده انجام شد؛ بررسی‌های تعریف‌شده ناسازگاری نشان ندادند |
| ۲. Workflow و Audit | رویدادهای تراکنشی، Timeline، زمان‌های واقعی، محافظت فرم قدیمی، مجوز درمانگر | هسته نصب شده؛ Timeline قابل نمایش و اصلاح آخرین مرحله با دلیل در نسخهٔ توسعه تست شد؛ اتصال Audit مالی/انبار در مراحل مربوط انجام می‌شود |
| ۳. Appointment Dashboard | فیلتر ترکیبی، آمار، هشتگ، شش ستون، بیشتر، نوع ویزیت، اتاق، تشخیص چندگانه، پکیج | فیلترهای ترکیبی، آمار، شش ستون، هشتگ، نوع ویزیت، تشخیص چندگانه و اصلاح اتاق/پکیج آمادهٔ توسعه؛ منوی بیشتر و اتصال مالی پکیج هنوز کامل نیست |
| ۴. نمایش | ستون/ترتیب/محدودهٔ نقش و Default/Lock مدیر؛ ترجیحات هر کاربر و Sidebar | برنامه‌ریزی‌شده |
| ۵. نوبت‌دهی | زمان آزاد، قفل جلوگیری از تداخل، ثبت سریع، پیشنهاد نوبت بعد | قفل و زمان آزاد موجود؛ تکمیل و تست هم‌زمانی لازم |
| ۶. درمان | حضور تا ترخیص، نتیجه فقط درمانگر مسئول، جلسه دهم واقعی، گزارش زمان | بخشی در هسته موجود؛ هشدار/گزارش نیاز به تکمیل |
| ۷. مالی | تخفیف، صورتحساب، پرداخت، بدهی و Audit متصل به Workflow | تعرفه و دفتر مالی موجود؛ تخفیف/اتصال نیاز به تکمیل |
| ۸. انبار و مدارک | مصرف اتمیک بدون موجودی منفی، نوع مدرک قابل توسعه | موجودی و آپلود موجود؛ مصرف نوبت/طبقه‌بندی نیاز به تکمیل |
| ۹. پیامک و گزارش | پیش‌نمایش مخاطبان فیلترشده، ارسال مجاز، روزانه/بازه‌ای/پیشرفت | صف پیامک موجود و غیرفعال؛ فیلتر و گزارش نیاز به تکمیل |
| ۱۰. Regression و Deploy | بقراط، اطلاعات قبلی، مالی، جلسات، انبار، Permission و سناریوهای هم‌زمان | فقط پس از مراحل بالا |

## قیود داده و مدل

- Patient: `patients`؛ Appointment/Session: `physio_sessions`؛ Treatment Plan: `physio_episodes`؛ Visit State/Event: `visit_workflows` / `visit_events`.
- مالی بومی `physio_payments` و `physio_episodes.fee_toman` از `patient_account_ledger` و آرشیو مالی Import جداست. برای تجمیع، نباید رکورد وارداتی دوباره صورتحساب شود.
- انبار `inventory_items` / `inventory_movements`: موجودی شروع NULL یعنی نامعلوم؛ اقلام وارداتی با `affects_stock=0` نباید بدون مبنای معتبر از موجودی کم شوند.
- اتاق در `resources(kind=room)` و نام اتاق در Session/Slot است. بیمه نباید جایگزین یا نام جدید اتاق باشد؛ ابتدا ستون‌های واقعی دیتابیس بررسی شوند. نسخهٔ فعلی فایل‌های SQL مدل مستقل بیمه ندارد.
- شش ستون: اطلاعات مراجعه، زمان نوبت، درمانگر، وضعیت بیمار، تشخیص‌ها، پکیج/عملیات.
- لیبل/هشتگ از دادهٔ واقعی سیستم خوانده شود. دادهٔ نمایشی ساختگی وارد دیتابیس زنده نشود.
- شمارش جلسه دهم فقط جلسات انجام‌شده است؛ کنسلی و غیبت محاسبه نشود. سوابق بقراط تنها پس از تطبیق هویت و جلوگیری از تکرار به شمارش اضافه شوند.
- نتیجه فقط توسط درمانگر منصوب به همان نوبت؛ نمایش اطلاعات تماس، مالی و فرم تابع Permission مستقل است.
- منوی بیشتر: پرونده، ویرایش، طرح درمان، نوبت بعد، تراز مالی، فرم ویزیت، مدارک، چاپ، پیامک، بیمه، چت و بازگشت مرحله. اتصال خارجی بیمه/چت نباید با دکمهٔ نمایشیِ بدون عملکرد جایگزین شود.
- پیامک در استقرار فعال نشود و تست‌ها پیام واقعی ارسال نکنند.

## یافته‌های Audit کد

- مهاجرت‌ها با SQL تکرارپذیر انجام می‌شوند؛ جدول تاریخچهٔ Migration وجود ندارد. داشتن جدول به‌تنهایی اثبات اجرای تمام تغییرات آن فایل نیست.
- Workflow فعلی از Row Lock و version استفاده می‌کند؛ Audit رویداد جلسه با وضعیت در یک تراکنش نوشته می‌شود. زمان‌های جلسات قدیمی عمداً NULL می‌مانند.
- Audit عمومی فقط actor/action/entity دارد؛ نوع موجودیت، مقدار قبلی/بعدی و ارتباط با پرونده برای همهٔ عملیات ثبت نمی‌شود.
- `inventory_adjust` بررسی و ثبت موجودی را در تراکنش با قفل کالا انجام نمی‌دهد؛ قبل از مصرف کالا و تست هم‌زمانی باید اصلاح شود.
- برنامه/غیبت درمانگر خارج از قفل رزرو تغییر می‌کند؛ برای تضمین Slot و Double Booking به بازبینی مشترک نیاز دارد.
- ویرایش مبلغ دوره و برخی تغییرات مالی تاریخچهٔ قبل/بعد کامل ندارند؛ مالی وارداتی باید جدا حفظ شود.
- بکاپ موجود PHP را متوقف می‌کند ولی به‌تنهایی تایمر واردکننده را متوقف نمی‌کند؛ بکاپ نهایی باید مانند مسیر ارتقا پس از توقف تایمرها و اطمینان از نبود Worker گرفته شود.

## Audit فقط‌خواندنی

`deploy/audit-clinic.php` در CLI یک تراکنش READ ONLY با snapshot باز می‌کند. خروجی فقط ساختار تجمیعی، شمارش، مجموع مالی، نقش‌ها و تعداد ناسازگاری است؛ نام بیمار، موبایل، متن پرونده، رمز و تنظیمات اتصال چاپ نمی‌شود. نتیجه روی سرور باقی بماند؛ اطلاعات عملیاتی واقعی وارد Git عمومی نشود.

NULL در بررسی یعنی ساختار لازم موجود نیست، نه اینکه آزمون موفق بوده است. شمارش Snapshot در حین فعالیت سیستم برای Audit مناسب است؛ مقایسهٔ پیش/پس Migration باید با نویسنده‌های متوقف انجام شود.

## وضعیت نسخهٔ توسعه

تغییرات پس از Audit زنده هنوز Deploy نشده‌اند. مرحلهٔ ۳ کامل اعلام نمی‌شود: شخصی‌سازی نمایش در مرحلهٔ ۴، پیشنهاد نوبت در مرحلهٔ ۵، اتصال مالی پکیج در مرحلهٔ ۷، مصرف کالا در مرحلهٔ ۸ و پیامک/گزارش در مرحلهٔ ۹ انجام می‌شوند. نوع ویزیت و تشخیص با Migration افزایشی appointments.sql ساخته می‌شوند؛ رویدادهای قبلی و مقادیر مالی بازنویسی نمی‌شوند.

اصلاح مرحله فقط آخرین تغییر اداری پیش از ثبت نتیجه را برمی‌گرداند، با Permission مستقل و دلیل اجباری. رویداد اصلی حفظ می‌شود؛ زمان‌های اصلاح‌شده در رویداد جدید قبل/بعد ثبت می‌شوند. فرم قدیمی، تغییر بدون مجوز، بازگشایی نتیجهٔ نهایی، نشت تشخیص به پذیرش و تغییر نصفهٔ مشخصات در تست‌ها بررسی شدند.
